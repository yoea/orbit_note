## 一、现有偏好设置项盘点（共 7 项）

入口：设置 → 通用 → 偏好设置（`components/PrefsDialog.tsx`）。

| # | 键 | 文案 | 默认 | 多端同步 | 性质 |
|---|---|---|---|---|---|
| 1 | `qo-offline-cache` | 离线缓存 | 开 | **否**（刻意不同步） | 能力开关 |
| 2 | `qo-location-enabled` | 保存时记录位置 | 开 | 是 | 隐私外发 |
| 3 | `qo-save-weather` | 保存时记录天气 | 开 | 是 | 隐私外发 |
| 4 | `qo-auto-place-name` | 自动补全地点名 | 开 | 是 | 隐私外发 |
| 5 | `qo-show-streak` | 显示连续写作天数 | 开 | 是 | 界面噪音 |
| 6 | `qo-show-prompt` | 显示每日提示 | 开 | 是 | 界面噪音 |
| 7 | `qo-show-on-this-day` | 显示去年的今天 | 开 | 是 | 界面噪音 |

**两条已经成立的规律（新增项应当遵循）：**

1. **默认一律「开」**，且都是「关掉某个能力」而不是「开启某个功能」——用户不动设置时得到的功能最全。
2. **只有 `qo-offline-cache` 是设备本地的**（不进 `ALL_KEYS`）：缓存是设备属性（手机开着、电脑可能关着），跨端同步开关会互相覆盖出错误状态。其余 6 项都是服务器同步的多端偏好。

**⚙️ 加一个偏好的固定代价（必须同时改三处，漏一处就是隐性 bug）：**

| 位置 | 漏了会怎样 |
|---|---|
| `lib/client/prefs.ts` 的 `ALL_KEYS` | 登录/解锁时拉不回服务器值 → 多端不一致（且只在一端表现） |
| `app/api/prefs/route.ts` 的 `PREF_KEYS` 白名单 | PUT 直接 400 → 只在本地生效，换设备就还原 |
| `components/PrefsDialog.tsx` 的 `rows` | 设置页看不到这个开关 |

> 建议后续给 `tests/` 加一条对账守卫：`PREF_KEYS` ⇄ `ALL_KEYS` 必须集合相等（现在两者靠人眼同步，而它们分处服务端与客户端两个文件）。

## 三、候选清单：建议纳入偏好设置的功能

### A 档 —— 建议做（收益明确、代价小）

**A1. 保存音效开关**（`playSaveSound`）
- **现状证据：** `components/DiaryEditor.tsx:318,337` 与 `components/EntryView.tsx:380,406` 共 4 处直接调用，全仓没有任何开关（`sound.ts` 自身也没有读取任何偏好）。它是**唯一一个会主动发出声音**的功能。
- **为什么要：** 声音是**环境敏感**的——图书馆、会议中、孩子刚睡着、戴着耳机。这一点与「深色模式」同类：不是审美偏好，而是「此刻合不合适」。
- **代价：** 极小。加一个 `qo-save-sound` 键 → 在 4 个调用点包一层 `if (isSaveSoundEnabled())`（可抽 `playSaveSoundIfEnabled()` 收敛成一个出口）。
- **默认值：** 开（保持现状）。

**A2. 主题外观（跟随系统 / 浅色 / 深色）**
- **现状证据：** 全仓暗色只有 `@media (prefers-color-scheme: dark)`（`app/globals.css:13,113`），**没有任何手动覆盖通道**；`app/layout.tsx:25-26` 的 `theme-color` 也只跟随系统。
- **为什么要：** 现在是「系统说了算，App 说了不算」。真实的失效场景：手机上为省电设了「日落后自动深色」，但你想在深夜写日记时保持柔和的浅色；或者反过来——白天系统是浅色，但你想在 OLED 上全程用深色省电。这类诉求在没有覆盖通道时**完全无法表达**。
- **代价：** 中等偏上，这是本清单里唯一「不是加个 if 就完事」的一项——注释里已写明全站约定「过渡只用 `transition-colors`」，改主题要在 `.dark` 类与 `prefers-color-scheme` 之间做取舍（Tailwind 4 下要给 `dark:` 变体换成 class 策略），并处理首帧闪烁（`<html>` 上需内联脚本在 paint 前打类）。**建议单独排期，不与其他偏好项混在一起做。**
- **默认值：** 跟随系统。

**A3. 保存位置时使用粗略坐标（≈1km）**
- **现状证据：** 发给第三方（BigDataCloud）的坐标早已模糊化——`coarsenCoordinate()` 保留 2 位小数 ≈ 1.1km（`lib/client/geocode.ts:5-11`）。但**入库的 `latitude` / `longitude` 是定位的原始精确值**，且随导出文件一起离开设备。
- **为什么要：** 这是本项目「数据流向透明」承诺下唯一还留着的锋利边缘：用户已经接受「坐标会上传」，但未必接受「精确到门牌号的坐标会永久留在服务器与备份里」而地点名其实只需要 1km 粒度。给了这个开关，隐私边界就从「我们来保证」变成「用户自己选」。
- **代价：** 小。保存前对坐标多走一次 `coarsenCoordinate`（该函数已有完整单测）；需要同步说明「开启后同一片地方会被归为同一个格子」。
- **默认值：** 关（保持精确）——改变既有数据的语义要用户主动选择。
- **⚠️ 注意：** 不要与 A2 混做；此项会改变新写入数据的精度，需要单独发版与迁移说明（**老数据不回填**）。

### B 档 —— 值得做（收益中等）

**B1. 打开次数（查看页眼睛图标）显示开关**
- **现状：** v1.18.6 新入库并显示在查看页底部操作栏左侧。
- **理由：** 是**统计属性最强**的一项元数据，强迫型用户不想看到「这篇只被我自己看了 1 次」这种数字。且它现在是操作栏的固定成员，占着一个视觉位。
- **代价：** 极小（隐藏一个图标 + 数字）。
- **注意：** 只应做成「隐藏展示」，**不要**做成「停止计数」——库里那个数字是「真实阅读历史」，停止写入等于让数据失真。若要停止计数，要在服务端加开关，成本与语义都更重。
- **默认值：** 显示。

**B2. 记住上次使用的导出格式（zip / JSON / CSV）**
- **现状：** 每次进「备份与恢复」都要重新选一次。
- **理由：** 属于「记住上次选择」类偏好，严格说不算设置项，但用户实际每周都会碰到。
- **代价：** 极小（localStorage 记一个字符串，**不同步服务器**——导出是设备本地行为）。
- **默认值：** zip。

**B3. 写作热力图显示开关**
- **现状：** 日记页顶部 `ContributionHeatmap` 固定渲染（最近半年）。
- **理由：** 占掉首屏约三分之一高度。只想「往下翻日记」的用户每次都要多滚一段。
- **代价：** 极小。
- **默认值：** 显示。

**B4. 「每日提示」的出现时机（总是 / 只在空白日记时）**
- **现状：** `qo-show-prompt` 只有开关，开着一进写页就占一行。
- **理由：** 老用户（提示已看过很多轮）更想要「安静的白纸」，但完全关掉又失去灵感提示。折中档位比二元开关更贴近真实使用。
- **代价：** 小（写页按 `plain.trim() === ''` 判断）。
- **默认值：** 总是（保持现状）。

### C 档 —— 不建议进偏好设置（附理由，避免反复讨论）

| 候选 | 为什么不建议 |
|---|---|
| 正文 Markdown 渲染开关（源码/预览） | 渲染是**产品定义**的一部分，不是风格。给开关等于维护两套渲染路径，还要额外回答「搜索/摘要/字数按哪套口径算」（现在派生层 `toPlainText` 是唯一口径）。真要看源码，编辑态本来就是源码。 |
| 列表密度 / 行高 | 只能做「紧凑/标准」两档，实际收益低于维护成本；且会与「底部安全区只由 TabBar 承担」「内容区自带 `pb-4`」这几条已定的布局约定打架。 |
| 每次打开都计数 / 不计数 | 属服务端行为，语义上不是「外观偏好」；且会让「打开次数」这一列的含义随设备而变（跨端不同步时两边数字不可比）。见 B1 的处理。 |
| 「编辑于」是否显示 | 它是**状态提示**（「这篇改过」），不是可选装饰；隐藏它会让人误以为正文从未被修改。 |
| 日期格式（绝对 / 相对） | 与「今天 / 昨天」的分组口径强耦合（`DiaryListView.dayLabel`），改一处要连带改分组与搜索排序展示，收益不成比例。 |
| 时区 / 天气数据源 | 技术参数，不是用户能有效决策的东西。 |

## 四、筛选维度：建议再补哪几项

现状（本次重构后）为三类：**时间**（全部 / 近 7 天 / 近 30 天 / 具体月份）、**收藏**（全部 / 仅收藏）、**地点**（全部地点 / 只看有位置 / 具体地点），外加关键词。

候选与理由（按「值不值得做」排序）：

1. **天气** —— 最强候选。
   - 数据已经在了：`weather` 是明文列，**而且已经是关键词检索字段**（搜「小雨」能命中）。
   - 差的是「列出来让我选」。用户的真实诉求是「找下雨天写的日记」「找那些阴天的低落记录」，这类诉求用关键词搜**覆盖不全**（正文没提天气的照样是阴天写的），必须靠筛选。
   - 成本：几乎为零——`locationFacets()` 换个字段就是 `weatherFacets()`，UI 与地点面板完全同构。**建议与地点合并为「地点与天气」一类，或作为第四类。**

2. **字数区间**（< 100 / 100–500 / > 500 字）
   - 数据已在库里（`word_count` 列，服务端可聚合）。
   - 诉求真实：想找「认真写过的长文」或「碎片记录」，靠关键词都做不到。
   - 成本：小（纯函数 + 面板一行）；选档位比让用户拖滑块更合适。

3. **星期**（周一 … 周日）
   - 从 `createdAt` 派生，零新增数据。
   - 诉求：「我是不是只在周末写」「周三那批记录有什么共性」——这是**自我观察**类需求，与热力图互补（热力图看密度、星期筛选看规律）。
   - 成本：小。

4. **打开次数**（从未看过 / 看过至少一次）
   - v1.18.6 刚入库，**现在才具备做这个筛选的数据条件**。
   - 诉求：找「写了就再没回看过的日记」——恰好是回顾类 App 最该推的场景（可以配合「去年今日」）。
   - 成本：小（服务端字段已明文）。
   - ⚠️ 前提：B1 若做成「隐藏展示」，筛选仍应可用（筛选是主动动作，不是被动展示）。

5. **「编辑过 / 从未编辑」**（`updatedAt !== createdAt`）
   - 零新增数据，直接派生。
   - 诉求：找「后来改过的那批」（通常是内容更重要的），或「一次写成、从未回改的原始记录」。
   - 成本：极小。
   - ⚠️ 注意与「打开次数不更新 `updatedAt`」的约定配合——回看不会被误判成编辑。

6. **年份**（在月份清单里按年分组）
   - 不新增数据，只是把现在的月份清单按年份折叠成两段（如「2026 年」「2025 年」）。
   - 诉求：日记攒到两三年后，一屏列 40 个月份已经不好选。
   - 成本：极小，且是**月份清单的自然演化**，建议等月份条目真的变多时再做（现在做等于提前优化）。

7. **组合预设**（如「旅行日记」= 有位置 + 有天气）
   - 这不是新维度，而是「把一组常用条件命名保存」。放到偏远位置，先记录想法即可。

**不建议加入筛选的：** 时区（技术参数）、定位精度、加密版本、设备（多设备区分对单用户没意义）。

## 五、本次已落地的改动（2026-09-30）

**筛选重构为三类**（`lib/client/search.ts` + `components/SearchDialog.tsx`）：
- 时间：`TimeRange` 去掉 `'year'`，新增 `'m:YYYY-MM'`（具体月份）与 `rangeEnd()`（次月 0 点，**不含**）；月份清单 `monthFacets()` 从实际数据现取、新的在前。按用户要求严格只保留四档，**「今年」已移除**。
- 收藏：维持两态（全部 / 仅收藏），**刻意不做「未收藏」补集**。
- 地点：「只看有位置」不再是独立 chip，降为地点面板里的第二档（不限 / 只看有位置 / 具体地点 三档互斥）。
- UI 从 7 个并列 chip 收敛为 **3 个控件 + 一个条件性的「重置」**。

**🐞 修掉的 bug：按地点筛选不显示结果。**
- **真因不在筛选逻辑**（`matches` 一直是对的，`tests/search.test.ts` 的 C2/C3 就钉着「选地名 = 该地点全部条目」「收藏 ∩ 地名」）。
- 坏在 UI 接线：面板里的地点清单从**已解密条目**现取，而打开面板只 `setOpenPanel(true)`、**没有触发 `ensureLoaded()`**，于是「进搜索 → 直接点地点」永远是空面板（提示「还没有记录过地点」），用户根本选不出地点。
- 修法：所有开面板的调用统一走 `openFilterPanel()`，该函数内必调 `ensureLoaded()`；空态文案区分「正在解密 / 真的没有 / 加载失败」三种情况。
- 防回归：新增 `tests/search-filters-ui.test.ts`（F0~F9），核心是 F2——**所有 `setOpenPanel(非 null)` 的调用都必须落在 `openFilterPanel()` 内**；并用 `Temp/nonvacuous_filters.py` 做了 8 个破坏用例的非空转验证（8/8 全部按预期变红并 md5 还原）。

## 六、第二轮已落地的改动（2026-09-30，A1 / A2 / B 档）

用户拍板执行 **A1 + A2 + B 档全部四项**（**A3 保存位置用粗略坐标明确未选**）。

### A1 保存音效开关 —— `qo-save-sound`（默认开，走服务器同步）
- `lib/client/sound.ts` 抽出唯一出口 `playSaveSoundIfEnabled()`（内部 `isSaveSoundEnabled()` 门控，关闭时连 `AudioContext` 都不创建）。
- 4 个调用点全部改走它：`DiaryEditor.tsx`（离线队列路径 / 在线路径）、`EntryView.tsx`（未同步笔记编辑 / PATCH 路径）。

### A2 主题外观（跟随系统 / 浅色 / 深色）—— `qo-theme`（**纯本地，不同步服务器**）
- **实现策略**：不改成 class 策略。本项目 279 处 `dark:` 工具类走 Tailwind 默认的 `@media (prefers-color-scheme: dark)`，改写全量类名风险高、收益低。
  因此：`system` 档 = 无类（跟随媒体查询）；`dark` 档 = 加 `.dark`（当前媒体查询下已正确）；`light` 档 = 加 `.theme-light`，由 `globals.css` **末尾**的反向压制表逐类覆盖（`.theme-light .dark\:bg-neutral-800` 特异性 0,2,0 > Tailwind 裸类的 0,1,0）。
- **首帧防闪**：`app/layout.tsx` 的 `<head>` 内联同步脚本读 `qo-theme` 并打类（`useLayoutEffect` 晚于首帧，不够）。
- **代价**：压制表是「按当前实际用到的 dark: 类」手工汇总的 —— 新增 `dark:` 工具类时必须同步补一行。**守卫 `tests/prefs.test.ts` 的 A2-4 扫全仓实际用到的 dark: 类，缺一条即红**（写这条守卫时抓出了 3 处真实遗漏：`placeholder:` / `active:` 两个变体）。

### B1 打开次数显示开关 —— `qo-show-views`（默认开，走服务器同步）
- 只隐藏**展示**（`EntryView` 的眼睛图标），`bumpEntryViewCount` 照常上报。守卫 B1-2 断言计数调用不被偏好包裹。

### B2 记忆上次导出格式 —— `qo-export-format`（**纯本地**）
- `ExportView` 首次仍是 `json-zip`（推荐），之后记住上次选择。因不再固定默认档，正文措辞从「（默认）」改为「（推荐）」。

### B3 热力图显示开关 —— `qo-show-heatmap`（默认开，走服务器同步）
- `DiaryListView` 的 `ContributionHeatmap` 渲染条件加偏好。

### B4 每日提示出现时机 —— `qo-prompt-timing`（`always` / `empty`，默认 `always`，**纯本地**）
- `'empty'` 档只在正文为空时显示（有内容就收起，把版面让给正文）。
- **★ 连带修掉一处失真**：`reportPromptShown(promptIdx)` 原先只要 `promptIdx` 变化就上报，与提示是否真的渲染无关；引入时机档后必须改为 `if (isPromptVisible) reportPromptShown(...)`，否则会出现「提示没显示但出现次数 +1」。守卫 B4-3 钉住。
